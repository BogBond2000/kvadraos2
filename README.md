# System Monitor — real‑time resource monitor (web UI, C++ backend, POSIX shared memory)

![Linux](https://img.shields.io/badge/platform-Linux-blue)
![C++](https://img.shields.io/badge/C%2B%2B-17-blue)
![TypeScript](https://img.shields.io/badge/TypeScript-5.0-blue)
![License](https://img.shields.io/badge/license-MIT-green)

**System Monitor** – это легковесное приложение для мониторинга загрузки процессора, памяти, swap, load average и топ процессов на Linux‑машине. Данные отображаются в веб‑интерфейсе в реальном времени (обновление каждую секунду).

Архитектура построена на двух независимых процессах, обменивающихся данными через **POSIX shared memory** с синхронизацией через мьютекс. Веб‑сервер на C++ отдаёт статику и JSON API, а фронтенд на TypeScript обновляет UI.

## Особенности

- **Метрики в реальном времени** – обновление данных каждую секунду.
- **Загрузка CPU** – общая и по каждому ядру (в процентах).
- **Память** – используемая, свободная, доступная, swap.
- **Load Average** – 1, 5, 15 минут.
- **Топ процессов** – до 20 процессов с наибольшим потреблением CPU (с именем, PID, CPU%, RSS).
- **Веб‑интерфейс** – современный адаптивный дизайн с прогресс‑барами.
- **Независимые процессы** – collector собирает данные, webserver отдаёт их. При падении одного, второй продолжает работу.
- **Юнит‑тесты** – проверка парсинга `/proc` данных (Google Test).

## Архитектура

### Компоненты

Приложение состоит из трёх логических частей:

```
┌─────────────────┐      ┌─────────────────┐      ┌─────────────────┐
│   Collector     │      │  Shared Memory  │      │   Web Server    │
│  (C++ process)  │ ───► │   (POSIX shm)   │ ◄─── │   (C++ process) │
└─────────────────┘      └────────┬────────┘      └────────┬────────┘
│                        │
pthread_mutex_t                 │
(межпроцессная                  │
синхронизация)                 │
▼
┌─────────────────┐
│   Browser       │
│  (HTML/CSS/TS)  │
└─────────────────┘
```

#### 1. Collector (`sysstat_collector`)

- Читает системные файлы `/proc/stat`, `/proc/meminfo`, `/proc/loadavg`, `/proc/[pid]/stat`.
- Вычисляет производные метрики (загрузку CPU по ядрам, использование памяти, топ процессов).
- Записывает структуру `SharedStats` в разделяемую память.
- Блокирует мьютекс перед записью, чтобы веб‑сервер не читал несогласованные данные.

#### 2. Shared Memory (POSIX)

- Создаётся collector'ом при старте и удаляется при его завершении.
- Содержит:
  - `pthread_mutex_t` с атрибутом `PTHREAD_PROCESS_SHARED` – для синхронизации между процессами.
  - Все числовые метрики + массив структур `ProcInfo` для топ процессов.
- Имя: `/sys_monitor_shm` (константа `SHM_NAME`).

#### 3. Web Server (`sysstat_webserver`)

- Прослушивает порт 8080.
- Отдаёт статические файлы (`index.html`, `style.css`, `main.js`) из папки `webui/`.
- Предоставляет REST API: `GET /api/stats` → возвращает JSON со всеми метриками.
- При каждом запросе блокирует тот же мьютекс, читает данные из разделяемой памяти и отвечает.

#### 4. Frontend (TypeScript)

- Каждую секунду делает `fetch('/api/stats')`.
- Парсит JSON и обновляет DOM: числовые значения, ширину прогресс‑баров, таблицу процессов.
- Не требует перезагрузки страницы.

### Поток данных

1. **Collector** запускается первым. Создаёт shared memory, инициализирует мьютекс. Входит в бесконечный цикл:
   - Берёт мьютекс.
   - Читает `/proc`, заполняет `SharedStats`.
   - Отпускает мьютекс.
   - Спит 1 секунду.

2. **Web Server** запускается вторым. Открывает существующую shared memory (не создаёт). При старте начинает слушать HTTP.

3. **Браузер** загружает `http://localhost:8080`. Сервер отдаёт `index.html`, `style.css`, `main.js`.

4. **main.js** запускает `setInterval(refresh, 1000)`:
   - `fetch('/api/stats')`
   - В обработчике сервера:
     - Блокируется мьютекс.
     - Читаются поля структуры.
     - Формируется JSON.
     - Мьютекс освобождается.
   - Ответ приходит в браузер, обновляется UI.

### Почему shared memory?

**Задача**: передавать большой объём структурированных данных (десятки полей + массив процессов) от collector'а к веб‑серверу с минимальной задержкой.

| Механизм      | Плюсы                                      | Минусы                            | Почему не подошёл?                    |
|---------------|--------------------------------------------|-----------------------------------|---------------------------------------|
| **Shared memory** | Нулевое копирование, максимальная скорость | Требует синхронизации, сложнее | ✅ **Идеально** – данные читаются мгновенно |
| Сокеты (TCP)  | Простота, масштабируемость                 | Копирование, сериализация         | Избыточно для IPC на одной машине      |
| Файл          | Проще всего                               | Медленно, износ SSD, нет синхронизации | Не подходит для real‑time             |
| DBus          | Стандарт Linux, хорошая синхронизация      | Тяжеловесный, накладные расходы   | Overkill для мониторинга               |

**Вывод**: shared memory даёт минимальную задержку и максимальную пропускную способность, что критично для отображения метрик в реальном времени.

### Почему два процесса?

Можно было сделать один процесс, который и собирает данные, и отдаёт HTTP. Но разделение даёт:

- **Отказоустойчивость**: если collector упадёт (например, из-за ошибки чтения `/proc`), веб‑сервер продолжит отдавать последние корректные данные (или покажет ошибку). Если упадёт веб‑сервер – сбор данных не прекратится.
- **Безопасность**: collector может работать с повышенными привилегиями (если нужно читать чужие процессы), а веб‑сервер – с минимальными (только чтение shared memory и статики).
- **Гибкость**: можно перезапустить веб‑сервер (например, сменить порт) без потери данных.
- **Простота разработки**: каждый процесс решает одну задачу.

---

### Синхронизация – почему мьютекс?

Два процесса одновременно читают и пишут одну область памяти. Без синхронизации возможны:

- **Гонка данных** (data race): collector обновляет структуру, а веб‑сервер читает её посередине. В результате веб‑сервер увидит частично записанные значения (например, `num_top_procs` уже новый, а сам массив ещё старый).
- **Некорректные показатели** (например, CPU > 100% или отрицательная память).

Использован `pthread_mutex_t` с атрибутом `PTHREAD_PROCESS_SHARED`. Это стандартный механизм для синхронизации между разными процессами в POSIX‑системах.

**Альтернативы**, которые мы отвергли:
- `sem_wait` (семафоры) – тоже подходят, но мьютекс более привычен для защиты критической секции.
- Lock‑free структуры – сложны в реализации и отладке, избыточны для нашего сценария (один писатель, один читатель, низкая частота обновления).

## Сборка и запуск

### Требования

- **Ubuntu 22.04** (или любой дистрибутив с Linux kernel 2.6+)
- **g++** (версия 11+), **cmake** (3.14+), **make** или **ninja**
- **Node.js** и **npm** (для компиляции TypeScript)
- **TypeScript** (устанавливается через npm)

Установка всего необходимого одной командой:
```bash
sudo apt update
sudo apt install -y g++ cmake make nodejs npm
sudo npm install -g typescript
```

### Сборка backend

```bash
git clone https://github.com/your-repo/system_monitor.git
cd system_monitor
mkdir build && cd build
cmake ..
make -j$(nproc)
```

В папке `build` появятся два исполняемых файла:
- `sysstat_collector`
- `sysstat_webserver`

### Сборка frontend

```bash
cd ../webui
tsc   # скомпилирует main.ts → main.js
```

Убедитесь, что в папке `webui` присутствуют `index.html`, `style.css`, `main.js`.

### Запуск

1. **Запустите collector** (в отдельном терминале):
   ```bash
   ./sysstat_collector
   ```
   Он начнёт писать данные в shared memory. На экран ничего не выводится (работает в фоне).

2. **Запустите веб‑сервер** (в другом терминале):
   ```bash
   ./sysstat_webserver
   ```
   Должно появиться сообщение: `Web server listening on http://localhost:8080`

3. Откройте браузер и перейдите на `http://localhost:8080`

4. Для остановки нажмите `Ctrl+C` в обоих терминалах. Collector автоматически удалит объект shared memory.

**Примечание**: Если вы видите ошибку `shm_open open failed: No such file or directory` – сначала запустите collector.

## Возможные улучшения (если бы было больше времени)

- **Исторические графики** (с использованием Chart.js или SVG).
- **WebSocket** вместо polling (снизит задержку и нагрузку на сервер).
- **Поддержка macOS/FreeBSD** (через условную компиляцию: `#ifdef __linux__` vs `#ifdef __APPLE__`).
- **Конфигурационный файл** (порт, путь к статике, интервал обновления).
- **Детализация по процессам** (вывод всех полей из `/proc/[pid]/status`).
- **Docker‑образ** для простого развёртывания.
- **Асинхронный I/O** в веб‑сервере (httplib поддерживает многопоточность, но можно перейти на Boost.Asio).
